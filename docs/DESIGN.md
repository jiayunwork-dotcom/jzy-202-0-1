# 设计决策

本文档记录粗能力计划（RCCP）服务的关键取舍：负荷展开规则、增量维护方案，
以及它们对结果口径、内存、并发和重启恢复的影响。

## 1. 负荷展开规则

产品 p 在第 t 周完工 q 件，它在工作中心 w 上的负荷为 `q × 单件工时 h`，
落在第 `t − L` 周（L 为 BOM 行上的提前量，单位周，可以是小数）。
两个需要拍板的点：

### 1.1 小数提前量 → 按比例拆分到相邻两周（本服务的规则）

把 L 拆成整数部分 f 和小数部分 r（L = f + r，0 ≤ r < 1）：

- 负荷的 **(1 − r)** 落在第 **t − f** 周
- 负荷的 **r** 落在第 **t − f − 1** 周

例：L = 1.5、第 3 周完工 10 件、单件 2h → 第 2 周 10h、第 1 周 10h。

被否决的备选方案：

| 方案 | 效果 | 偏差 |
|---|---|---|
| 整体归前一周（L 向上取整） | 负荷全部压到更早的一周 | **偏悲观**：那几周被高估，可能把还得及的订单误判为超负荷 |
| 整体归后一周（L 向下取整） | 负荷全部推迟到更晚的一周 | **偏乐观**：近处的周被低估，可能漏判超负荷 |
| **比例拆分（采用）** | 总量无偏，峰值摊到相邻两周 | 对单个周而言介于前两者之间：比"归前"乐观、比"归后"悲观 |

比例拆分背后的假设是"工作量在提前量覆盖的时间跨度内大致均匀发生"，
与周粒度的粗能力计划相匹配；它严格保持总量守恒和线性（数量 ×k → 负荷 ×k）。

### 1.2 落到计划期开始之前的负荷 → 单列"逾期负荷"（本服务的规则）

完工周 − 提前量 < 1 的负荷，按工作中心累计到 **past_due（逾期负荷）** 桶，
在负荷矩阵和超负荷清单里单独报告，不并入任何周。

| 方案 | 效果 | 偏差 |
|---|---|---|
| 丢弃 | 总量不再守恒 | **偏乐观**："已经来不及做"的工作量被隐藏 |
| 累到第 1 周 | 第 1 周虚高 | **偏悲观**：历史欠账与当周真实需求混为一谈，扭曲排产信号 |
| **单列逾期（采用）** | 总量严格守恒：所有周负荷 + 逾期 = Σ 数量 × 单件总工时 | 中性：缺口显式可见，由计划员决定加班/外包/推迟 |

## 2. 增量维护 vs 每次全量展开

**选择：草稿的负荷矩阵常驻内存、增量维护；全量展开只用于三个时刻。**

- **增量更新**：编辑单元格 (产品 p, 周 t)：old → new 时，只对 p 的每条 BOM 行
  把差量 `(new − old) × h` 按提前量规则加进矩阵。复杂度 O(每个产品的 BOM 行数)，
  单次编辑远低于 1ms——计划员改一个格子立刻能看到负荷变化。
- **全量展开**（O(非零计划格 × 每产品 BOM 行数)，几百产品 × 20 周 × 几行 ≈ 几万次
  加法，毫秒级）只用于：
  1. **服务启动**：从 SQLite 持久化的草稿重建内存矩阵；
  2. **资源清单发布新版本**：BOM 是展开的结构输入，换版本后整矩阵重建；
  3. **发布 / 按新清单重算**：生成要持久化的历史快照。
- 能力日历只影响"能力对比"，不影响负荷矩阵，日历换新版本不需要重建。

### 对内存的影响

每份草稿一张矩阵：`工作中心数 × (周数 + 1) 个 float64`。
几十个工作中心 × 21 列 × 8 字节 ≈ **几 KB**；计划本身只存非零格
（内存稀疏字典 + SQLite 表）。已发布版本的负荷结果以 JSON 存进 SQLite，
每份也是 KB 级。整体内存开销可以忽略。

### 对并发写入的影响

- **单进程单写者**：所有修改（编辑、批量导入、发布、换 BOM/日历版本）在同一个
  `asyncio.Lock` 下串行执行，**按到达顺序生效**。锁的临界区是一次单元格更新
  （微秒级），多名计划员改不同格子实际上互不阻塞。
- **同格冲突（CAS）**：逐格编辑必须携带 `expected_old_qty`（调用方基于的旧值，
  新格子为 0）。与当前值不一致 → `409` 并返回当前值，由调用方重新读取后再试。
  批量导入的每一行可选携带 `expected_old_qty`，带了就校验；任一行失败整批回滚。
- 读操作直接读内存快照（numpy 数组拷贝 / 已持久化结果），不加锁。
- 若未来需要多实例水平扩展，串行点要下沉到数据库（行锁或单写者队列）；
  当前规模（几十工作中心 × 20 周）单实例绰绰有余，不在本服务范围内。

### 对重启恢复的影响

SQLite（WAL 模式）只保存**源数据**：BOM/日历的各版本、草稿单元格、
已发布计划版本及其负荷结果。草稿的负荷矩阵是**派生状态，不持久化**，
启动时从持久化的草稿一次全量展开重建（毫秒级）。

- 每次编辑立即提交事务，已确认的编辑不会因重启丢失；
- "重启后矩阵与崩溃前内存矩阵逐格一致"由性质保证：增量维护 ≡ 全量展开
  （`tests/test_incremental.py` 用 2000 次随机修改 + 中途切换 BOM 版本证明），
  而启动重建做的就是全量展开。

### 数值精确性

数量是整数；当单件工时与小数提前量取二进制有限小数（0.5、0.25、1.5…）时，
所有中间和都能被 float64 精确表示，增量累加与全量展开 **bit 级相同**
（测试用 `np.array_equal` 断言）。一般十进制小数（如 0.3）时差异在 1e-12
相对误差量级（测试用 `allclose` 断言）。

## 3. 版本与绑定

- **资源清单 / 能力日历**：创建即不可变，每次创建产生新版本号，`current` 指向最新。
- **主生产计划**：单一共享草稿 + 不可变的已发布版本。发布时冻结草稿副本，
  绑定当时的 BOM 版本与日历版本，负荷结果（kind=publish）一并持久化。
- 已发布结果**不因** BOM/日历出新版而自动改变。
- **按新清单重算**：对同一计划版本用指定（缺省当前）BOM/日历重新展开，
  存为 kind=recompute 的新结果，并返回与 publish 结果的对比；原结果保留。
- **版本对比**：两个版本各自使用自己绑定的日历判定超负荷——即使负荷相同，
  日历变化也会被报告为状态翻转。

## 4. 校验与提示

拒收（422）：数量为负或非整数（整数值浮点如 3.0 接受）、单件工时为负、
提前量为负、能力为负、周号超出 1..计划期、引用不存在的产品（任何 BOM 版本
都没有）或工作中心、BOM 版本内重复行、日历版本内重复条目、批量导入中任一
非法行（整批回滚，错误按行号汇总）。

提示（不拒收）：草稿引用了"已知、但当前 BOM 版本未覆盖"的产品（例如新清单
删掉了它）→ 响应的 `warnings.products_without_bom` 列出这些产品，其负荷按 0 计。

同格冲突：409 + 当前值。前置条件不满足（如无日历版本时查超负荷、无 BOM/日历时发布）：409。

## 6. 规模估算

几百产品 × 20 周 × 每产品数条 BOM 行：全量展开约几万次浮点加法。
实测（500 产品 × 30 工作中心 × 20 周、约 7000 个非零计划格、1500 条 BOM 行）：
全量展开约 21ms，增量编辑约 5µs/次，负荷矩阵约 5KB。
SQLite 单文件即可，无外部依赖。
